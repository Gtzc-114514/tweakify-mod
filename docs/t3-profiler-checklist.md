# T3 实机 profiler 验证检查表

本清单对应 [`docs/tech-debt.md`](tech-debt.md) 的 T3（扫描与收集仍在主线程分帧执行）。
T3 的触发条件是：profiler 确认 `BlockMarkerScanner.tick` 或 `AttackRangeState.tick` 占主线程超过约 5%，
或收到“开启屏障可见后卡顿”的可复现反馈。两者是独立触发路径：未收到复现反馈且占比未达 5% 之前，T3 保持暂缓。

## 一、前置条件

- 客户端版本与待测提交一致：记录 `git rev-parse --short HEAD` 与 `gradle.properties` 的 `version`；
- 安装 Spark（推荐）或准备 JFR；
- 固定配置：屏障/基岩扫描半径 32、刷新 6 次/秒、基岩标记上限默认 32、攻击范围收集距离 48 / 上限 64；
  屏障标记上限为代码内固定的 256（不可配置）；
- 记录硬件：CPU 型号、内存、图形后端（OpenGL/Vulkan）、游戏内渲染距离。

## 二、场景矩阵

每个场景以“静止 60 秒 + 移动 60 秒”为 1 轮，共 3 轮（冷启动 1 轮、热缓存 2 轮），每轮单独记录一行：

| # | 场景 | 功能配置 | 目的 |
| --- | --- | --- | --- |
| A | 屏障密集自制地图（≥300 个屏障；标记上限 256 会截断，超出部分不影响扫描负载，只影响粒子/几何） | 只开屏障可见 | 最坏屏障场景 |
| B | 下界顶棚（单层基岩，y≈127） | 只开基岩高亮 | 最坏基岩场景 |
| C | A + B 同时开启 | 两项全开 | 合并扫描负载 |
| D | 普通主世界空旷区 | 两项全关 | 对照组 |
| E | 刷怪场或村庄（≥64 生物，超过上限 64 时只保留最近的） | 攻击范围开启（距离 48、上限 64） | 实体收集侧 |

## 三、采集步骤

### Spark（推荐）

1. `/spark health` 记录整体 TPS/MSPT；
2. 进入场景后执行 `/spark profiler start --timeout 120`；
3. 静止 60 秒后开始移动 60 秒；
4. `/spark profiler stop`，保存火焰图链接；
5. `/spark tickmonitor --threshold-tick 50` 观察超过 50 ms 的 tick（避免每条 tick 都输出）。

### JFR（备用）

推荐进入场景后按 PID 启动，避免把启动/加载期算进窗口：

```text
jcmd <pid> JFR.start name=scan settings=profile duration=120s filename=scan.jfr
jcmd <pid> JFR.stop name=scan        # 需要提前结束时
```

启动参数 `-XX:StartFlightRecording=...` 只在无法连接 jcmd 时使用，且需自行扣除启动与加载时间。
用 JMC 打开 `scan.jfr`，过滤 `Render thread`（若名称不同以实际客户端主线程名为准），检索
`BlockMarkerScanner.tick` / `ScanJob.step` / `scanLayer` / `AttackRangeState.tick`。

## 四、采集项与数据清单

| 项 | 说明 |
| --- | --- |
| 火焰图占比 | 按 `Render thread` 过滤后的视图中，`BlockMarkerScanner.tick` / `AttackRangeState.tick`（含子调用）的累计采样百分比（分母为该线程总采样） |
| MSPT | `/spark health` 的 p50 / p95 / p99（注：该值为集成服务端 tick 时间，仅作旁证） |
| FPS | 每轮分段（静止/移动各 60 秒）的平均值与 1% low |
| 扫描规模 | 每轮 section 预筛命中数、进入逐方块读取的层数、命中标记数（屏障/基岩各取上限前） |
| 快照等价量 | 按命中 section 数换算的 `copy()` 体积（section 数 × 2–4 KB），用于评估快照方案的每 tick 预算 |
| 元数据 | 维度、坐标、种子、实体数、已加载区块数、CPU、渲染距离、图形后端 |
| 日志 | `logs/latest.log` 中的异常、GC 告警与 Tweakify 相关 warning |
| 原始文件 | Spark 链接或 JFR 文件名（原始大文件不入库，只记录链接/文件名与摘要） |

## 五、判定标准

| 结果 | 判定 |
| --- | --- |
| 收到“开启屏障可见后卡顿”的可复现反馈（不要求占比达标） | 已满足 T3 触发条件，按反馈复现路径定位后决定是否启动预案 |
| `BlockMarkerScanner.tick` 或 `AttackRangeState.tick` 占比 **> 5%**，或 A/B/C/E 的帧时间（FPS 1% low 或 Render thread 采样）相对 D 明显恶化且可复现（p95 MSPT 差值可作辅助证据） | 满足 T3 触发条件；先按建议方案 3 评估降低刷新频率/缩小半径/降低上限是否够用，不足再启动“主线程快照 + 后台解析”预案 |
| 占比 **2%–5%** 且无复现反馈 | 继续观察；优先考虑降低刷新频率、缩小扫描半径或降低标记上限 |
| 占比 **< 2%** 且无复现反馈 | 维持现状，并在 `docs/tech-debt.md` 的 T3 状态写为“复测未达触发条件（YYYY-MM-DD）”，保留本表作复测基线 |

## 七、结果处理

- 达标：先按建议方案 3 评估降负手段，不足再按“主线程快照 + 后台解析”预案实施，先提交可回滚的分步计划再动手；
- 不达标：T3 状态写为“复测未达触发条件（YYYY-MM-DD）”，保留本表作为后续复测基线；
- 任何场景出现崩溃或明显卡顿：先记录 `logs/latest.log` 与 Spark/JFR 证据，再按“可复现卡顿反馈”条件重新评估；
- 若 profiler 显示的线程名不是 `Render thread`，以实际客户端主线程名为准。
